## 0. 設計の理由ひとめ（なぜこのルートなのか）

- **なぜ全程細かいグリッドではなく段階的（S0→S1→S2）なのか？** SCF の初期サイクルでは \|ΔE\| が、粗いグリッドや VV10 をまだ計算しないことによる誤差より数桁大きいため、序盤に安い設定を使っても収束先の解は変わりません。\|ΔE\| と \|g\| がグリッド誤差と同程度まで下がってから切り替えます。切り替えのたびにエネルギー汎関数が変わるので、DIIS をリセットし Fock を完全に再構築します。この方式は Engine（実運用の MD プログラム）で検証済みです。
- **なぜ重い計算は FP32 で GPU へ、仕上げは FP64 で CPU に残すのか？** コンシューマー GPU（RTX 30/40/50）の FP64 スループットは FP32 の 1/64 で、全部を GPU FP64 で実行しても割に合いません。SCF のエネルギーは収束点で密度行列に対して停留（δE = O(‖δD‖²)）なので、FP32 段階は収束への経路だけに影響し、収束先の解には影響しません。最後に CPU FP64 の K と半局所 XC の仕上げでエネルギーを FP64 の不動点に固定します（本体との差は実測約 1e-8 Ha）。
- **なぜ gpu4pyscf をそのまま使わないのか？** gpu4pyscf は全程 FP64 で A100 クラスのカードを対象にしています。本プロジェクトはコンシューマーカード上の COSX K と VV10 を対象とし、kernel はすべて自作（CuPy RawKernel）です。gpu4pyscf は libxc-cuda の提供者としてのみ、点ごとの汎関数評価という「軽い計算」に使い、`XcFunctional` インターフェースの後ろに隠します。なければ CPU libxc にフォールバックします。
- **なぜ誤差制御が設計の中核なのか？** FP32 のランダムな丸め誤差は相殺されます。本当に危険なのは系統的なバイアスで、原因は二つ：定数の丸め（すべての積分が同じ向きにずれる → 定数は FP32 hi+lo のペアで保存し `fmaf` で補償）と、コヒーレントな丸め（原子中心グリッドでは同じ radial 殻の角度方向の点が同じ AO 値を見るため、誤差が同じ向きに加算され系のサイズに比例して増える → K 経路では X・2 つの GEMM・グリッド重みを FP64 のままにし、F だけを一度丸める）。
- **なぜ PySCF 主導 + 取り外し可能な hook にこだわるのか？** fork せず、site-packages を書き換えず、シグネチャを変えません。GPU が無い場合やエラー時は自動で CPU 参照パスにフォールバックします。上流の更新と比較検証が容易です。
- **なぜ VV10 のタイル刈り込みは安全なのか？** VV10 カーネルは遠距離で 1/R⁶ で減衰し、タイル間の最小距離と W0・κの極値から厳密な上界を作ります。`vv10_tile_tol = 0` なら厳密計算と一致します。刈り込みは FP32 計算のタスクを減らすだけで、数学は変えません。
- **なぜ K 側の戦略層（experimental/cosx）を凍結したのか？** サイクルごとの controller、SR スクリーニング、dynamic A/B は gate をすべて通過できず、複雑さに見合う利益がありませんでした。メインラインは「段階的 + GPU FP32 + FP64 の仕上げ」のままで受け入れ目標を達成しています。
- **なぜ RI-JK と勾配は対象外なのか？** RI-JK の GPU 適応精度はすでに発表済み（Huang, Shao, Hammond 2026）で、再発明しません。勾配は上流の PySCF 2.14 のバグ（SGX グリッド応答をオンにすると勾配が NaN）のため上流の修正を待ちます。

## 1. 背景と動機

- **stock PySCF のボトルネックは VV10。** water27・def2-SVP・ωB97M-V・RIJCOSX での実測：VV10 が SCF 時間の 65%、半局所 XC 部が 9%、2 つの K が合計 24%。原因は `nlcgrids` のデフォルトが level 3 で、`_vv10nlc` が O(N_g²) の密計算だからです。
- **実運用の MD プログラム（以下 Engine）はすでに VV10 を 5% まで下げています**（remdesivir、1755 基底関数、8 コア）。方法は二つ：VV10 を段階的にオンにすること、粗いグリッドを使うこと。Engine では残るボトルネックは COSX の K で 64% です。
- **コンシューマー GPU の性能差。** gpu4pyscf（JPCA 129, 1459、arXiv:2407.09700）は全程 FP64 で、A100 でのみ計測されています。RTX 30/40/50 系列の FP64 は FP32 の 1/64 です。Huang・Shao・Hammond の研究（JPCA 130, 3483, 2026）は、RI-JK に適応精度 + INT8 を使えば RTX 4090 で 204% 速くなり、収束エネルギーは影響を受けないことを示しました。RI-JK はすでに済んでいるため、**本プロジェクトは繰り返しません**。

## 2. 目標と非目標

**目標**：RIJCOSX で ωB97M-V を計算し、**単一の大きな系**の SCF レイテンシを短縮する。コンシューマー GPU 上で CPU+GPU のヘテロ構成とし、重い計算は FP32 で GPU へ、FP64 が必要なものは CPU へ。

**ハードウェア前提**：
- 開発は RTX 2080 Ti（sm_75、TF32 なし）。
- 正式な実行は RTX 3090/4090/5090（sm_80 以上）。
- **CPU 側は 16 コア基準で設計・検収**。GPU 搭載機の一般的な構成です。
- 「FP64 の GPU」という選択肢はありません：コンシューマーカードの FP64 スループットは低すぎるため、**GPU FP64 kernel を過渡案にはできません**。

**受け入れ**：SCF エネルギーのみを見ます。最終結果を「全程細かいグリッド・全 FP64」の参照値と比べ、誤差 < 1e-4 Ha。

**非目標**：
- RI-JK：Huang 2026 がすでに実施。
- 核勾配（力）：今後の課題。
- バッチスループット：今回は単一系のレイテンシが目標。
- site-packages の変更：PySCF は 2.14.0 に固定。取り外し可能な hook のみ使用。
- git 操作は行わない（プロジェクトのルール）。

## 3. 全体アーキテクチャ（案 1'）

- **SCF は引き続き PySCF が CPU 上で駆動します。** GPU が引き取るのは 2 つの入口だけ：`ni.nr_rks`（XC）と `ni.nr_nlc_vxc`（VV10）。シグネチャも戻り値も PySCF と同じです。
- **計算量で精度を決める**：
  - **重い計算**、すなわち O(N_g·nao²) の GEMM と O(N_g²) の VV10 のペアごとの和は、GPU 上で **FP32** で実行。
  - **軽い計算**、すなわち O(N_g) の点ごとの演算と O(nao²) の累積は **FP64 でもよく**、しかも 16 コア CPU への負担を減らすためなるべく GPU に置く。
- **CPU（FP64）に残すもの**：SCF の主流程、COSX の K（PySCF SGX + `sgx_patch`）、RI-J、対角化、DIIS、直交化。
- **K は将来移す**：16 コア機では K が次のボトルネックになるため、K は `KBuilder` インターフェースの後ろに置き、S5（GPU FP32 版 COSX）で置き換える。

## 6. 精度方針と段階（S2、S3）

**段階**（切替のたびに 3 つの作業：グリッド変更、DIIS リセット、Fock の完全再構築。**同じ段階内ではグリッド・精度・tolerance は不変**）：

| 段階 | 開始条件（暫定、実験で調整） | XC グリッド（`grids.level`） | VV10（`nlcgrids.level`） | COSX（SGX グリッドレベル） |
|---|---|---|---|---|
| S0 | 初期推定から | 1 | オフ | 1 |
| S1 | \|g\| < τ₁ = 1e-3 | 3 | オン、1 | 1 |
| S2 | 隣接 2 サイクルの \|ΔE\| < 1e-6 Ha | 3 | 3 | 2 |

- **参照値**（「全程細かいグリッド・全 FP64」）の定義：stock PySCF、XC は level 3、VV10 は level 3、SGX は level 2（いずれも PySCF 2.14 のデフォルト）。`sgx_patch` を適用し、conv_tol は被験案と同じ。
- したがって S2 は参照値と同じグリッドを使っており、段階的化の誤差は S0・S1 が残した収束経路の違いにのみ由来し得ます。
- **VV10 には 2 つの使い方があります**（パラメータ `vv10_mode`）。Engine の実測では両者は同等です：
  - `'late_scf'`（デフォルト）：上の表に従い S1 と S2 で自己無撞着に VV10 を計算。
  - `'nonscf'`：SCF 中はまったく VV10 を計算せず、収束後に最終密度で 1 回だけ VV10 エネルギーを評価。VV10 を分散補正として使う形で、最も安い選択肢です。受け入れはエネルギーのみを見るため正式な選択肢であり、受け入れ時には `'late_scf'` と \|ΔE\| を比較します。
- **S2 には 2 つのモードがあります**（パラメータ `s2_mode`）：
  - `'converge'`（デフォルト）：S2 内で conv_tol まで収束。誤差は収束閾値と同程度で、1e-4 Ha を大きく下回ります。
  - `'steps'`：S2 では `s2_steps` ステップだけ実行（デフォルト 1）。Engine と同じ方式で、誤差は 1e-4 Ha まで許容する代わりに高グリッドのサイクル数を減らします。
  - 受け入れでは両モードを測定し、誤差と所要時間をそれぞれ報告します。

ここでの \|g\| は PySCF の `envs['norm_gorb']` で、`track_residual` 経由で読みます。DIIS のリセットは `mf.callback` 内で `envs['mf_diis']` を取得し、その `_buffer`・`_bookkeep`・`_head`・`_H`・`_xprev` をクリアする方法で行います。

**演算子ごとの精度**：

| 演算子 | 場所 | 精度 |
|---|---|---|
| AO 評価（φ、∇φ） | GPU | FP32 |
| density_gemm（ρ、∇ρ、τ） | GPU | FP32 SGEMM |
| XC 汎関数評価（点ごと） | GPU | FP64。gpu4pyscf の libxc-cuda（軽い計算）；将来 JAX FP32 に変更可 |
| fock_gemm（Vxc、Vnlc） | GPU | ブロックごとに FP32 で部分行列を作り、GPU 上で FP64 で累積 |
| VV10 kernel_sum、O(N_g²) | GPU | FP32 のタイル分割、タイル内は Kahan 補償付き加算。格子点ごとの F・U・W は FP64 で累積 |
| エネルギーの和 | GPU または CPU | FP64 |
| K、RI-J、対角化、DIIS | CPU | FP64 |
| TF32 | — | **デフォルトはオフ**。S0 の GEMM でのみ明示的に許可、sm_80 以上に限る。TF32 を FP32 とみなしてはならない |

**誤差予算**：
- 混合精度による誤差：同じグリッドで、全 FP64 と比べ < 1e-6 Ha。
- 段階的化とグリッドによる誤差：全程細かいグリッド・全 FP64 の参照と比べ < 1e-4 Ha。
- S2 の最後のステップはデフォルトで GPU の FP32 バックエンドを使いますが、< 1e-6 Ha を満たすことが前提。満たさなければ CPU 上の FP64 参照実装にフォールバック。

## 7. GPU バックエンドのインターフェースとデータフロー（S3）

**各段階に入るとき**：CPU 上で NumPy により、グリッド（座標は分子中心からの相対値を FP32 で保存、重みも一緒）、ブロックリスト（AO の疎パターン、形状ごとにバケット化）、FP32 でパックした基底パラメータを準備し、GPU メモリに常駐させます。

**各サイクル**：
- DM をアップロード（nao²）。
- バケットごとに GPU 上で順に実行：XC フロー（AO → ρ/∇ρ/τ → libxc → fock_gemm → Vxc）と、VV10 フロー（専用グリッド上で：AO → ρ/∇ρ → W0、κ → kernel_sum → F/U/W → fock_gemm → Vnlc）。
- Vxc + Vnlc（nao²）とエネルギーをダウンロード。

**GPU メモリ**：バケットごとにストリーミング使用。N_g × nao 全体の配列は保存しません。ブロックサイズはメモリ予算で決め、デフォルトは空きメモリの 60%。

**kernel_sum のタイルペア刈り込み**：VV10 カーネルは遠距離で約 1/R⁶ で減衰します（g ≈ R²·W0）。タイルのペア (I, J) ごとに、タイル間の最小距離とタイル内の W0・κの極値から Σ q_i·q_j·M_ij の上界を計算し、閾値 `vv10_tile_tol` 未満のペアは丸ごとスキップします。上界は CPU 上で NumPy により計算し、GPU は残ったタイルペアだけを処理します。`vv10_tile_tol = 0` では刈り込まず、結果は厳密計算と一致し、受け入れの対照に使います。

**インターフェース**（まず CuPy 版を実装、名前は `'cupy'`。将来 `'jax'` を追加。両者は DLPack でゼロコピー交換）：

```python
class AoEvaluator:   eval(block) -> ao32                      # (ncomp, npts, nao_active)
class XcFunctional:  eval(rho) -> exc, vrho, vsigma, vtau
class Vv10Kernel:    kernel_sum(coords, q, W0, kappa) -> F, U, W
class KBuilder:      get_k(dm, omega)                         # 現在は CPU 上の SGX。S5 で GPU に置換
```

**エラー時の扱い**：
- GPU や CuPy がない：自動で CPU 参照パスにフォールバックし、警告を出します。
- GPU メモリ不足（OOM）：ブロックサイズを半分にして再試行。
- kernel_sum はタイル分割のリダクションを使い、atomicAdd は使わない。結果は実行ごとに再現可能です。

**実装言語**：まず CuPy + RawKernel（CUDA C）。JAX は後から 2 番目のバックエンドとして接続します。注意は 3 点：静的形状（バケット化 + パディングで解決）、`precision='highest'`（XLA のデフォルト TF32 を防ぐ）、`XLA_PYTHON_CLIENT_PREALLOCATE=false`（CuPy とメモリを奪い合わないため）。Zig はオプションで、スケジューリングがプロファイルでボトルネックと証明された場合のみ検討します。

## 7.5 S3b：VV10 を分離化し低ランク圧縮する（O(N_g²) → 約 r·N log N）

**動機**：stock PySCF で VV10 は 65% を占めます（§1 の実測）。S3 の GPU FP32 は定数倍しか速くしません。S3b は計算量そのものを下げます。

**文献**：
- rVV10：Sabatini ら、PRB 87, 041108 (2013)。Román-Pérez–Soler 補間に適するようカーネルを書き換えたもの。
- ωB97M-rV：Mardirossian ら、JPCL 8, 35 (2017)。b = 6.2 を推奨。B97M-rV は B97M-V と同等かそれ以上の性能。
- Gaussian 軌道系での rVV10 の RPS + FFT 実装：Lee ら、JCP 155, 164102 (2021)。Q-Chem GPW、O(N_g log N_g)。

**方法**（**元の VV10 を維持**し、最終的に計算するのは厳密に ωB97M-V）：
1. **2 次元補間**。元のカーネルは Φ = −3/2 · 1/[g·g′·(g + g′)]、g = κ(qR² + 1)、q = ω₀/κ。(g + g′) が κ と κ′ を同時に含むため、q だけの補間では不十分で、(q, κ) の 2 次元補間が必要：θ_{ab}(r) = ρ(r) · p_a(q(r)) · p_b(κ(r))。場の数は M = M_q × M_κ。
2. **共通因子の低ランク圧縮**。K_{(ab),(cd)}(R) ≈ Σ_{s=1}^{r} A_{(ab),s} · A_{(cd),s} · f_s(R)。因子 A は R に依存しない（対称性制約付き CP 分解）。r 本のチャネルだけが残る：ρ_s = Aᵀθ、E ≈ ½ Σ_s ⟨ρ_s, f_s ∗ ρ_s⟩。ポテンシャル側は v_θ = A·(f_s ∗ ρ_s) とし、p_a・p_b の導関数チェーンで vrho と vsigma に戻します。
3. **畳み込み**：r 本のチャネルそれぞれで radial 畳み込みを 1 回。分子グリッド上の候補は 2 つで、spike B が決めます：
   - 均一グリッドに投影し、padding を付けた開境界 FFT；
   - f_s(R) が遠距離で R⁻⁶ で減衰することを利用し、tree 法や多重極法で Becke グリッド上に直接計算。
4. **段階ごとの使い方**（§6 の `vv10_mode` と組み合わせ）：S1 は S3b（または rVV10 近似）を安い VV10 として使える。S2 の最後のステップは S3 の厳密な FP32 ペア和、または誤差予算内の高精度設定の S3b を使う。切替時は例どおり DIIS をリセット。

**着工前の 2 つの spike**（SCF も GPU も不要、NumPy で可能）：
- **spike A（ランク）**：(q, κ, q′, κ′, R) グリッド上で元のカーネル（および対照として rVV10 カーネル）を表化し、R ごとの SVD と共通因子の CP 分解を実施。ε = 1e-6、1e-5、1e-4 の相対誤差に対する r(ε) と必要な M_q × M_κ を報告。
- **spike B（エネルギー）**：water27 の収束密度を使い、VV10 グリッド上で分離化 + 低ランクのカーネルを**直接二重和として**計算（まだ畳み込み加速はしない）し、密で厳密な E_nl と比較。判据：補間と打ち切りの誤差 ≤ 1e-5 Ha。最終的な 1e-4 Ha 予算に余裕を残します。その後、2 つの畳み込み案の精度と速度を比較。

**S3b の受け入れ**：S3 の厳密版を対照に、|ΔE_nl| ≤ 1e-5 Ha、フル SCF の |ΔE| ≤ 1e-4 Ha。同じグリッドで、VV10 の所要時間は S3 の厳密 GPU 版よりさらに 1 桁下げること。

## 8. テストと受け入れ

pytest マーカー：`gpu`（GPU がなければ自動スキップ）、`slow`、`experimental`（デフォルトでは実行しない）。

**第 1 層：kernel ごとの CPU FP64 との比較**（2080 Ti で実施）

| kernel | 参照 | 判据 |
|---|---|---|
| AO 評価 | `mol.eval_gto` | 相対誤差 ≤ 1e-6（max\|φ\| 基準） |
| ρ、∇ρ、τ | numint `eval_rho` | 相対誤差 ≤ 1e-6 |
| libxc-cuda | PySCF の libxc | ≤ 1e-12 |

| XC エネルギーと Vxc | `nr_rks`（同じグリッド） | \|ΔE\| ≤ 1e-7 Ha |

**第 2 層：フル SCF**（water27、chain30）
- グリッド固定、混合精度のみを見る：|ΔE| ≤ 1e-6 Ha、サイクル数の差は 1 以内。
- 段階的：「全程細かいグリッド・全 FP64」の参照と比べ、|ΔE| ≤ 1e-4 Ha、追加サイクルは最大 2。
- 堅牢性：hook の着脱で完全に元に戻る。GPU がなくても CPU にフォールバック。OOM 時はブロックサイズを半分にして続行。

**第 3 層：性能**（RTX 30/40/50 系のマシン、`OMP_NUM_THREADS=16`。2080 Ti は機能確認のみ）
- ベースライン：同じマシン上の stock PySCF、16 スレッド、最終グリッドは同じ。
- **G_gpu1**：同じグリッドで、GPU 版 VV10 + XC の所要時間は CPU 版の 0.1 倍以下。
- **G_gpu2**：段階的フル実行の総 SCF 時間はベースラインより 2 倍以上速く、|ΔE| ≤ 1e-4 Ha。
- 各項目で記録：部分時間、サイクル数、GPU メモリのピーク、PCIe 転送量。

**テスト体系**：単体テストは water dimer、統合テストは water27 と chain30。実分子は後日選定。

## 8.5 S5（COSX）着工前に答えるべき問い：長距離 exchange に専用の数値積分体系を持たせるか

**問い**：K_LR は erf(ωr)/r カーネルを使います。full COSX と同じグリッド・スクリーニング・精度閾値を共有すべきか、それとも独自の体系（専用の COSX グリッドさえ）を持つべきか。

**既存データ**（water27 と chain30 の実測。§1 と同じ帰属データ）：
- **スクリーニングにはもうほとんど削減の余地がない**：stock では full と LR のタスク数はほぼ同じ（2930 万対 2854 万）。oracle もどの誤差予算でも保持タスク数はほぼ同じ。局所性は F = P·X 自身の減衰に由来し、積分カーネルには依存しません。
- **同じグリッドでは LR の方が不正確**：SGX level 2 で、解析 K と比べたグリッド誤差は full 5.1e-7 Ha、LR 4.3e-6 Ha、SR 4.8e-6 Ha。推測では `fit_ovlp` の誤差相殺が full の 1/r を前提に設計されているため。未検証。
- **LR のコストは確かに高い**：積分 1 個あたり full の 1.45〜1.7 倍、K build 1 回で 1.3〜1.5 倍遅い。格子点数を半分にすれば、LR のオーバーヘッドもほぼ半分になります。

**判定実験**（PySCF 内で実施、工数は小さい）：
- SGX はもともと ω ごとに独立のコピー `_rsh_df[key]`（独自の `_pjs_data` を持つ）を作っており、勾配の RSH 分岐もこのコピーを再利用します。LR コピーのグリッドレベルを 1 に、full を 2 に保つだけで十分です。
- water27 で 3 つを測定：LR のグリッド誤差（解析 K と比較）、LR の K build 時間、フル SCF の \|ΔE\|。
- **結論の下し方**：
  - LR の誤差が 1e-4 Ha を大きく下回り、時間が約 0.5 倍に：独立グリッドは実施の価値があり、Engine への移植も価値がある。
  - LR の誤差が明確に増える：必要なのは独立グリッドではなく、LR 専用の誤差補正（たとえば LR 専用の overlap fitting）。
- **収束の安定性**：SCF 全体で不変の LR グリッドは DIIS を乱しません。避けるべきは SCF の途中で変更することです。

**元素感度**（Engine での経験：COSX グリッドは元素によって敏感なものとそうでないものがある）：
- **PySCF の現状**：SGX の opt grids は radial 点数が周期で変わるだけ（`SGX_RAD_GRIDS[level, period]`）で、角度方向の格子点は Bragg 半径で剪定（`sgx_prune`）。同じ周期の元素は同じグリッドで、たとえば C・N・O・F は完全に同一。元素ごとの感度設定はありません。
- **そのまま使えるインターフェース**：`grids.atom_grid[symb] = (nrad, nang)` で元素ごとにグリッドを指定できます。
- **感度実験**：
  - 他の元素のグリッドは変えず、毎回 1 元素だけグリッドを 1 レベル上げ、K のエネルギー変化を記録（解析 K と比較、または最高レベルのグリッドと比較）。
  - full と LR で別々に実施。両者の元素感度は異なる可能性があるためです。
  - 結果は「元素 × グリッドレベル → 誤差寄与」の表になります。
- **用途**：元素ごとにグリッドを設定。敏感な元素は細かく、鈍感な元素は 1 レベル下げ、総誤差予算を固定したまま格子点数を最小化します。この考え方は XC グリッドと VV10 グリッドにも同じく適用できます。

## 10. リスク

| リスク | 緩和策 |
|---|---|
| FP32 の AO や ρ の誤差が非線形の XC で拡大する | 第 1 層で項目ごとに定量化。S2 は CPU FP64 にフォールバック可能 |
| 段階の切替点が不適切でサイクル数が増える | 切替時に DIIS をリセット。τ₁ は実験で調整。受け入れ判据にサイクル数を含める |
| libxc-cuda（gpu4pyscf 由来）のインターフェースが不安定 | `XcFunctional` の後ろに包む。PySCF の libxc が常に参照 |
| 16 コア機で K がボトルネックになり G_gpu2 に届かない | G_gpu2 は 2 倍に設定し余裕を持たせる。K は S5 に委ねる |
| ブロック形状の多様さで kernel 起動オーバーヘッドが増える | 形状ごとにバケット化。小さすぎるブロックは CPU に残す |
